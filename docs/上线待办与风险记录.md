- [x] ~~**P0-3 · NAS 每日自动同步实际没有在跑**~~
  (**2026-08-26 第 59 轮已修复,并跨过真实触发时刻实测**)。
  根因是用 `_seconds_until(sync_time) > 60` 反推"是否到点":该函数在 `target <= now` 时
  把目标推到第二天返回约 86400,而 `time.sleep()` 保证在截止时刻**当时或之后**才醒,
  于是醒来那一刻必然被判成"还差 86400 秒",当天同步被直接跳过。
  改为「今天的计划时刻已到,且今天还没跑过」,并把"今天跑过没有"从**进程内存移到数据库**
  (原 `last_run` 重启即丢,在计划时刻前后重启可能同日跑两次——同一处的第二个隐患)。
  判据抽成纯函数 `_due(now, hhmm, last_auto)`,12 个注入时刻全部符合预期;
  端到端验证:把同步时间设到 3 分钟后并重启,**20:42:00 准点自动执行**
  (`status=success`,日志有对应行),测试记录已清理、配置已还原为 01:00。
  副作用(有意为之):服务若在计划时刻之后才启动、当天又没跑过,会在 1 小时内补跑一次。
  `run_sync` 只处理 `nas_synced=False`,补跑幂等且廉价,这让"昨晚机器没开"能自愈。

## 巡检记录

- **2026-08-27 第 74 轮(索引是否真的被当前查询用上)**:起点是一个针对**我自己**的怀疑——第 66 轮我把订单列表的 `ORDER BY created_at DESC` 改成了 `created_at DESC, id DESC`,而复合索引是 `(factory_id, created_at)`,多加一列排序很可能让 MySQL 退回 filesort,等于废掉第 43 轮的优化。

  **生产库上一看确实是 `key: NULL` + `Using filesort`。但这个结论是错的。** 做对照才发现:去掉 `id DESC` 的旧写法**计划完全相同**——127 行的表上 MySQL 一律选全表扫描,**这个规模下的执行计划说明不了任何问题**。差点把小表行为读成自己造成的性能回归。

  于是在**独立临时库**造真实规模数据重测(5 万订单 / 30 万审计日志,不碰生产)。结论与小表上看到的完全相反:

  | 场景 | 计划 |
  |---|---|
  | 管理员(`factory_id IN` 两个工厂) | `ix_orders_created_at` · **Backward index scan,无 filesort** · 扫 62 行 |
  | 普通用户(单工厂) | `ix_orders_factory_created` · **Backward index scan,无 filesort** |
  | 审计:默认列表 / 模糊查目标 / 时间窗 | 三类**全部走 `ix_audit_logs_created_at`、无 filesort** |

  **`id DESC` 兜底列是免费的**:InnoDB 的二级索引本就隐含追加主键,`(factory_id, created_at)` 实际等价于 `(factory_id, created_at, id)`,所以 `ORDER BY created_at DESC, id DESC` 天然可由反向索引扫描满足——单工厂查询带不带兜底列,计划一模一样。第 43 轮的索引与第 66 轮的兜底列**互不冲突**。

  **本轮未发现缺陷**,如实记录为已验证。实际产出是把一条模糊的 P2 变成了有数字的:审计模糊查询在三年规模下 **命中多时 0.10s、最坏 0.88s**(查不存在的值时要扫完整个索引),据此维持"不处理"的决定——但这次是有依据的,不是"看着还行"。顺带记录待办接口现网耗时 0.09s。
