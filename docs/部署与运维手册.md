# COO 资料收集平台 · 部署与运维手册

对应《需求规格说明书（一期）》8.3 节交付物。适用对象:IT 管理员/运维人员。

## 1. 系统组成

Docker Compose 单机部署,包含 5 个服务:

| 服务 | 说明 | 端口(宿主) |
|------|------|------------|
| frontend | Nginx:静态页面 + `/api` 反向代理,**唯一对外入口** | 80(启用 HTTPS 后加 443) |
| backend | FastAPI 应用(uvicorn 单进程,非 root 运行) | 127.0.0.1:8000(仅本机,供调试/vite dev) |
| mysql | MySQL 8.0 业务数据库 | 127.0.0.1:3307(仅本机;宿主 3306 已被其他服务占用) |
| minio | S3 兼容对象存储,模拟/承接 NAS 归档 | 127.0.0.1:9000 / 9001(仅本机) |
| zenko | 测试用 S3 服务(严格语义交叉验证),含公开默认密钥 | 127.0.0.1:8001(仅本机,生产可删除该服务) |

数据落盘:MySQL → `mysql_data` 卷;MinIO → `minio_data` 卷;附件主存 → `./data/uploads` 目录挂载;NAS 本地回退目录 → `./nas_mount`。

## 2. 部署步骤

```bash
cd /srv/platform/code/coo-docs
docker compose build
docker compose up -d
docker compose ps          # 确认 5 个服务均为 running/healthy
```

首次启动自动完成:建表、生成 JWT 签名密钥(存库,不在任何配置文件中)、种子数据。

### 2.1 生产环境必做

1. **关闭演示账号**:backend 环境变量加 `SEED_DEMO_DATA: "false"`。全新数据库首次启动只创建 admin,随机初始密码打印在启动日志(仅一次):
   `docker compose logs backend | grep "初始密码"` — 登录后立即修改。
   (默认 `true` 时会创建 admin/admin123 等演示账号,仅限开发验收使用。)
2. **启用 HTTPS**:见第 3 节。
3. **配置每日备份**:见第 4 节。
4. **云安全组**:仅放行 80/443,来源限制为工厂出口公网 IP 白名单(规格 6.3 节);SSH 改非标准端口并限来源。
5. **轮换数据库/MinIO 口令**:compose 中为开发默认值,生产应修改(MySQL 需 `ALTER USER`,MinIO 改环境变量后重建容器并同步 backend 的 S3 凭据)。

## 3. 对外访问:Cloudflare Tunnel(当前生产方式)

生产入口为 **https://coo.chongzhu.ai**,通过本机既有的 Cloudflare Tunnel(systemd 服务 `cloudflared`,配置 `/etc/cloudflared/config.yml`)接入:

- ingress 规则:`coo.chongzhu.ai → http://localhost:80`(排在 catch-all 404 之前)
- HTTPS 由 Cloudflare 边缘终结;源站 80 端口仅绑定 127.0.0.1,不在局域网/公网暴露
- 真实客户端 IP 经 `CF-Connecting-IP` 头透传(nginx map → X-Real-IP),审计日志与限流按真实 IP 生效
- 修改 ingress 后:`sudo cloudflared tunnel --config /etc/cloudflared/config.yml ingress validate && sudo systemctl restart cloudflared`(注意该隧道同时服务本机其他站点,重启有秒级瞬断)
- 访问控制加固(可选,对应规格 6.3 的来源限制):在 Cloudflare Zero Trust 中对 coo.chongzhu.ai 配置 Access 策略(邮箱/国家/IP 白名单)

## 3b. 备选:源站直连 HTTPS(不走隧道时)

1. 准备证书(推荐 Let's Encrypt + certbot 自动续期),将 `fullchain.pem`、`privkey.pem` 放入 `./certs/`。
2. 用 `frontend/nginx-https.conf.example` 的内容替换 `frontend/nginx.conf`(域名改为实际二级域名)。
3. `docker-compose.yml` 的 frontend 服务:放开 `- "443:443"` 与 `./certs:/etc/nginx/ssl:ro` 两处注释。
4. `docker compose build frontend && docker compose up -d frontend`。
5. 验证:浏览器访问 `https://域名` 无告警,`http://` 自动 301 跳转。

## 4. 数据库备份与恢复

**备份**(规格:每日一次,保留 30 天):

```bash
# 手动执行
./scripts/backup_mysql.sh
# 加入 crontab(每天 02:00)
crontab -e
0 2 * * * /srv/platform/code/coo-docs/scripts/backup_mysql.sh >> /var/log/coo_backup.log 2>&1
```

备份产物在 `./backups/coo_日期.sql.gz`,自动清理 30 天前的文件。云主机每日快照(保留 7 天)在 UCloud 控制台配置。

备份脚本自带可用性自检:gzip 完整性 + 关键表建表语句存在,任一不满足即报错并删除残缺文件。

**恢复演练(建议每月一次)**——备份能生成 ≠ 能恢复,必须实际验证:

```bash
./scripts/restore_drill.sh              # 用最近一次备份演练
./scripts/restore_drill.sh backups/coo_2026-08-23_000703.sql.gz
```

演练恢复到独立的 `coo_restore_drill` 库(**不触碰生产数据**),逐表比对行数,再抽验中文编码、JWT 密钥、密码哈希、已放行锁定态、索引是否保真,结束后自动清理演练库。任一项不符即以非零退出码返回,便于接入告警。实测本环境恢复耗时约 2–4 秒,远优于规格要求的 RTO ≤ 8 小时。

**真实恢复**(确认要覆盖生产数据时):

```bash
gunzip -c backups/coo_2026-XX-XX_xxxxxx.sql.gz | \
  docker compose exec -T -e MYSQL_PWD=<密码> mysql mysql -ucoo coo
docker compose restart backend
```

注意:附件文件不在数据库备份内,恢复数据库后需用 `scripts/storage_check.py` 核对是否出现悬空记录(记录在、文件丢失),必要时从 NAS 副本补回。

附件目录 `./data/uploads` 建议随主机快照一并保护;NAS 侧留有每日同步副本(异地副本)。

## 5. NAS 归档同步

- **自动**:每日定时执行增量同步(默认 01:00)。时间与开关在「NAS 归档 → NAS 配置」中调整,**保存后即刻生效,无需重启**。
- **归档目标配置**:管理员在「NAS 归档 → NAS 配置」中维护接入方式(S3 兼容接口 / 本地挂载目录)、端点地址、Access/Secret Key、存储桶、区域、HTTPS 开关。配置存于数据库,保存后立即生效;库中无记录时回退到 backend 环境变量(老部署无需任何改动)。Secret Key **只写不读**——界面与接口都只返回掩码,留空提交表示保持不变。
- **务必先「测试连接」再保存**:改错地址或密钥若不试连,要等到当晚自动同步失败才会暴露,而那意味着该归档的核查证据当天没有留存。测试会区分"地址不通/密钥无效/桶不存在"给出具体原因,且不写库。
- 每次配置变更都会写入操作日志(`nas / config_update`,记录归档目标与同步时间,不含密钥)。
- **手动**:系统内「NAS 归档」页面点击手动同步;同页可查看上次同步时间、成功/失败清单、连通状态。
- **目录规范**:`/COO核查/{项目代号}/{资料包编号}_{名称}/{版本号}/文件`,每版本目录含 `manifest.txt`(清单+大小+MD5)。
- **同步失败处理**:查看「NAS 归档」页失败清单与 `docker compose logs backend`;常见原因为 S3 端点不可达或凭据错误(在「NAS 配置」里点「测试连接」即可定位)。失败文件下次同步自动重试。
- **隧道**:生产按规格书第四章用 frp/Tailscale 打通工厂 NAS,在「NAS 配置」中把端点地址指向隧道内的 NAS S3 兼容服务(群晖/威联通均支持);隧道中断只影响当日归档,恢复后自动补齐。

## 5b. 附件存储一致性巡检

附件按内容 sha256 命名落盘,数据库记录与物理文件应一一对应。定期巡检:

```bash
docker compose exec backend python scripts/storage_check.py                  # 只报告
docker compose exec backend python scripts/storage_check.py --purge-orphans  # 确认后回收孤儿文件
```

- **悬空记录**(库有记录、磁盘无文件)= **证据丢失**,审计调阅会 404。属紧急问题,需从 NAS 副本或数据库备份恢复。脚本以非零退出码返回,便于接入告警;NAS 同步也会把它报为「源文件缺失」。
- **孤儿文件**(磁盘有文件、库无记录)不影响正确性,但会静默占用数据盘。常见来源:数据库恢复到较早快照、直接用 SQL 清理记录、写库失败的残留。建议随每日备份一并巡检。

## 6. 安全运维

- **JWT 密钥轮换**:管理员登录 → 组织管理 → 安全设置 → 轮换密钥。用于怀疑令牌泄露或强制全员下线;轮换后所有人(含本人)需重新登录。密钥存于数据库 `system_settings` 表,不在代码/配置中。
- **账号锁定**:连续 5 次密码错误锁定 30 分钟(`MAX_LOGIN_FAILURES`/`LOGIN_LOCK_MINUTES` 可调);管理员可通过重置密码解锁场景处理。
- **接口限流**:登录 20 次/分钟/IP,其余 600 次/分钟/IP,超限返回 429(内置,无需配置)。
- **审计日志**:系统内无删除/修改入口,保留期内(≥3 年)勿清理 `audit_logs` 表。

## 7. 常见故障

| 现象 | 处理 |
|------|------|
| 页面 502 | backend 未就绪或崩溃:`docker compose logs backend`;nginx 每 10s 自动重解析 backend IP,容器重建后无需重启 frontend |
| 登录报"账号已锁定" | 等 30 分钟或管理员重置密码 |
| 上传报 400 超限 | 单文件上限 100MB(`MAX_FILE_MB`);nginx 请求体上限 200MB |
| PDF 预览空白 | 强制刷新(Ctrl+F5);确认 `/assets/*.mjs` 返回 `Content-Type: text/javascript` |
| 全员突然要求重新登录 | 属正常:JWT 密钥被轮换(查审计日志 `org.jwt_secret_rotate`)或后端首次生成密钥 |
| 宿主重启后服务未起 | 所有服务已配 `restart: unless-stopped`,若仍未起:`docker compose up -d` |

## 8. 升级

```bash
git pull
docker compose build
docker compose up -d      # 数据卷与上传目录不受影响
```

### 8.1 从旧版本(root 容器 / 环境变量密钥时代)升级的注意事项

1. **上传目录属主**:后端容器现以 uid 1000 运行。旧版本以 root 写入的文件会导致上传报 500,升级前执行:
   `sudo chown -R 1000:1000 ./data/uploads ./nas_mount`(目录不存在则先 `mkdir -p`,由部署用户创建即可)。
2. **全员重新登录一次**:JWT 密钥改为数据库存储,升级后首次启动生成新密钥,所有旧登录态失效,属预期的一次性影响。
3. **`SECRET_KEY` 环境变量已彻底失效**:设置它不会有任何作用;轮换密钥一律走界面(组织管理 → 安全设置)。
4. **已存在的演示账号不会被自动停用**:`SEED_DEMO_DATA=false` 只约束"新建",历史库中的 coo/dept_*/auditor 等账号仍然有效——请用组织管理中新增的「停用」按钮逐个停用,并修改 admin 密码。
5. **端口收敛**:3306/8000/9000/9001/8001 已改为仅绑定 127.0.0.1。此前从其他机器直连这些端口的工具(数据库客户端、BI 等)会连接失败,需改走 SSH 隧道:`ssh -L 3306:127.0.0.1:3307 用户@服务器`(宿主侧映射为 3307)。
6. **防自锁保护**:系统会拒绝停用当前登录账号,以及停用/降级最后一个启用状态的管理员。

注意事项:多进程/多实例部署不在一期范围——NAS 调度器与接口限流按单进程实现,横向扩容前需先改造(代码注释已标注位置);JWT 密钥轮换已支持多进程收敛(解码失败自动回源),但仍建议扩容前整体评估。
