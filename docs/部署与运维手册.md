## 1. 系统组成

Docker Compose 单机部署,5 个服务:

| 服务 | 说明 | 端口(宿主) | 数据 |
|------|------|------------|------|
| frontend | Nginx:静态页面 + `/api` 反向代理,**唯一对外入口** | 127.0.0.1:80 | 无状态 |
| backend | FastAPI(uvicorn 单进程,以 uid 1000 非 root 运行) | 127.0.0.1:8000(仅本机,供调试/vite dev) | 无状态 |
| mysql | MySQL 8.0 业务数据库 | 127.0.0.1:3307(宿主 3306 已被其他服务占用) | `mysql_data` 卷 |
| minio | S3 兼容对象存储,承接 NAS 归档 | 127.0.0.1:9000 / 9001 | `minio_data` 卷 |
| ~~zenko~~ | **测试用** S3 服务(严格语义交叉验证),含公开默认密钥。**已移出主 compose**,见 `docker-compose.test.yml`,仅开发期拉起 | 127.0.0.1:8001 | 无 |

**所有端口仅绑定 127.0.0.1**,外部流量一律经 Cloudflare Tunnel → nginx。

### 数据落盘位置

| 内容 | 位置 | 备份方式 |
|---|---|---|
| 业务数据库 | Docker 卷 `mysql_data` | `scripts/backup_mysql.sh` → `backups/coo_*.sql.gz` |
| 附件主存 | `./data/uploads`(宿主目录挂载) | **同一脚本** → `backups/coo_files_*.tar.gz`;另有 NAS 每日同步副本与主机快照 |
| ZIP 导出临时文件 | `./data/uploads/.zip-tmp` | 无需备份,见 §8.3 |
| NAS 本地回退目录 | `./nas_mount` | 归档副本 |
| MinIO 对象 | Docker 卷 `minio_data` | 归档副本 |
| 数据库备份产物 | `./backups/` | 建议另行异地拷贝 |

> **数据库与附件必须成对恢复**。附件表里的记录指向 `UPLOAD_DIR` 下**按内容 sha256 命名**的物理文件,
> 只恢复数据库会得到一堆指向不存在文件的记录——`storage_check.py` 会逐条报「悬空记录:证据丢失」。
> 备份脚本因此**同时打包两者**,`coo_*.sql.gz` 与 `coo_files_*.tar.gz` 带同一时间戳,恢复时请配对使用。
>
> NAS 上虽有第二副本,但归档路径用的是**原文件名**而非内容哈希,靠它重建 `uploads/` 需要逐个重算
> sha256 并改名,**没有现成脚本,不能当作恢复手段**——NAS 副本的定位是异地留存与核查调阅,不是恢复源。

#### 备份不会自动进 NAS,离机留存前必须先加密

备份产物只落在宿主的 `./backups`,**NAS 同步只处理附件表里的附件,不碰这个目录**。也就是说
备份与生产数据在同一台机器上:宿主损坏或中勒索软件,两者一起没。因此必须另行离机拷贝。

但**不要把未加密的备份放到 NAS 或任何共享位置**。数据库转储里含:

| 内容 | 后果 |
|---|---|
| `system_settings.jwt_secret_key`(**明文**) | 可离线伪造任意管理员令牌,绕过全部认证 |
| `nas_config.secret_key` | 可直接访问整个 NAS 归档 |
| `users.password_hash`(bcrypt) | 可离线暴力破解 |

NAS 是工厂共享设施,把备份丢进去等于把系统钥匙一并交出。正确做法是**先加密再离机**:

```bash
# 加密备份（口令务必与备份分开保管，否则等于没加密）
BACKUP_ENCRYPT_PASS='...' ./scripts/backup_mysql.sh
# 产出 coo_日期.sql.gz.enc 与 coo_files_日期.tar.gz.enc，明文当场删除

# 演练/恢复（脚本会自动解密到临时目录）
BACKUP_ENCRYPT_PASS='...' ./scripts/restore_drill.sh
```

未设 `BACKUP_ENCRYPT_PASS` 时脚本会告警并明确说明"仅可留在本机受限目录"。
加密用 AES-256-CBC + PBKDF2(600k 轮),加密后**立即验证能解开**——加密产物解不开等于备份作废。

### 关键设计约束(影响运维决策)

- **单进程部署**:接口限流为进程内内存计数、NAS 调度器为进程内线程。**横向扩容前必须先改造**
  (改为 Redis 共享计数 + 外部 cron),代码注释已标注位置。
- **JWT 密钥存数据库**,不在代码或配置中;支持多进程收敛(解码失败自动回源)。
  设置 `SECRET_KEY` 环境变量**没有任何作用**。
- **启动期自动补齐表结构**:`create_all` 只建表不改表,因此启动时会额外执行
  `_ensure_columns()` 与 `_ensure_indexes()`,为历史库补建后加的列与索引(已存在则跳过)。
  升级时**不需要手工迁移**;启动日志会打印如「已补建列 notifications.params」。

## 2. 部署

### 2.1 首次部署(客户机上用这一条)

```bash
cd <项目目录>
./scripts/install.sh
```

脚本做四件事,做完即是正确状态,**不需要再照着清单逐条补**:

1. **生成 `.env`**:数据库、对象存储、备份加密的随机口令(字母数字,40 位以内),权限 600。
2. **构建并启动服务**。
3. **追加 crontab**:每日 02:00 备份、每月 1 日 03:00 恢复演练。
   **追加而非覆盖**(宿主上可能有其他项目的任务);已装过则跳过,脚本可重复运行。
   日志默认落 `/var/log/`,不可写时回退到项目内 `logs/` 并告警。
4. **自检**并打印 admin 初始口令与备份加密口令的保管要求。

首次启动自动完成:建表、补列补索引、生成 JWT 签名密钥(存库)。
`SEED_DEMO_DATA=false` 已固化,全新库**只创建 admin**,不会有任何演示账号。

> **口令只在数据库首次初始化时生效。** 库建起来之后再改 `.env` 里的口令,
> 不会改掉库里的口令,只会让后端连不上——轮换已有部署见 §11.3。
>
> **`.env` 不存在时服务会直接拒绝启动**(compose 用 `${VAR:?}`),
> 而不是静默回落到某个弱默认口令。这是有意的:起不来看得见,弱口令上线看不见。

手工部署(不推荐,仅在需要逐步控制时使用):

```bash
cp .env.example .env && vi .env      # 必填:两个 MYSQL_* 口令、两个 MINIO_* 口令
docker compose up -d --build
docker compose ps                    # 确认服务均为 running/healthy
```

### 2.1b 改动后端代码后的部署顺序(务必按此)

```bash
docker compose build backend
./scripts/preflight.sh               # ← 不能跳过
docker compose up -d backend
```

`docker compose build` **不执行 Python**——语法错误或坏掉的 import 会一路通过构建,
直到容器启动才崩,而那时坏代码已经在生产上了。第 72 轮就这么把线上打断过约一分钟
(一处多行 import 被改成 `from x import a, (`,构建通过、部署上去、站点返回 000)。
`preflight.sh` 在**构建好的镜像里真正导入一次应用**,失败时打印具体文件与行号并以非零退出。
正反两向均已实测:正常代码退出 0;故意改坏 import 后退出 1 并指出 `todo.py:9`。

### 2.2 拿到 admin 初始密码

生产模式(`SEED_DEMO_DATA=false`,compose 中已固化)下,全新数据库首次启动**只创建 admin**,
随机初始密码打印在启动日志,**仅打印一次**:

```bash
docker compose logs backend | grep "初始密码"
```

登录后立即在「组织管理」外的**右上角头像 → 修改密码**改掉,并**删除任何记录了该密码的临时文件**。

### 2.3 环境变量

**口令类配置一律在 `.env`**(见 `.env.example`),`docker-compose.yml` 只引用不存值——
`.env` 已在 `.gitignore` 中,不会进版本库。其余运行参数在 compose 的 `backend.environment`。

`.env` 中的项:

| 变量 | 说明 |
|---|---|
| `MYSQL_ROOT_PASSWORD` / `MYSQL_PASSWORD` | 仅首次初始化数据库时生效;**只能用字母数字**——会被拼进 `DATABASE_URL`,`@ : / ? #` 会被当作 URL 分隔符 |

| `TIMEZONE` | 影响 NAS 定时同步与超期判断,**必须按客户所在地确认** |
| `CORS_ORIGINS` | |
| `BACKUP_ENCRYPT_PASS` | 设了才会加密备份产物(§6.1);**必须与备份分开保管** |

其余变量的完整清单:

| 变量 | 默认值 | 说明 |
|---|---|---|
| `DATABASE_URL` | `sqlite:///./coo.db` | compose 中设为 MySQL 连接串 |

| `DEBUG` | `false` | |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `480` | 会话 8 小时 |

## 3. 对外访问:Cloudflare Tunnel(当前生产方式)

生产入口 **https://coo.chongzhu.ai**,经本机既有的 Cloudflare Tunnel
(systemd 服务 `cloudflared`,配置 `/etc/cloudflared/config.yml`)接入:

- ingress 规则:`coo.chongzhu.ai → http://localhost:80`(必须排在 catch-all 404 之前);
- HTTPS 由 Cloudflare 边缘终结;源站 80 端口仅绑定 127.0.0.1,不在局域网/公网暴露;
- 真实客户端 IP 经 `CF-Connecting-IP` 头透传(nginx map → `X-Real-IP`),**审计日志、运行日志与限流均按真实 IP 生效**;
  伪造的 `X-Real-IP` 会被 nginx 覆写忽略;
- 修改 ingress 后:
  ```bash
  sudo cloudflared tunnel --config /etc/cloudflared/config.yml ingress validate
  sudo systemctl restart cloudflared
  ```
  ⚠️ **该隧道同时服务本机其他站点,重启有秒级瞬断**,请安排在低峰。

### 3b. 备选:源站直连 HTTPS(不走隧道时)

1. 准备证书(推荐 Let's Encrypt + certbot 自动续期),把 `fullchain.pem`、`privkey.pem` 放入 `./certs/`。
2. 用 `frontend/nginx-https.conf.example` 的内容替换 `frontend/nginx.conf`(域名改为实际二级域名)。
3. `docker-compose.yml` 的 frontend 服务:放开 `- "443:443"` 与 `./certs:/etc/nginx/ssl:ro` 两处注释,
   并把 80 端口的绑定从 `127.0.0.1:80` 改为 `0.0.0.0:80`。
4. `docker compose build frontend && docker compose up -d frontend`。
5. 验证:浏览器访问 `https://域名` 无告警,`http://` 自动 301 跳转。

## 4. nginx 与前端资源策略

- **请求体上限 200MB**(`client_max_body_size 200m`),与后端 `MAX_FILE_MB=100` 一致且留有余量。
  调大 `MAX_FILE_MB` 时**必须同步调大 nginx 上限**,否则大文件会在 nginx 层被 413 拒绝。
- **`/health` 有独立 location** 反代到后端并标 `no-store`——探活结果不被任何中间层缓存。
  (曾经它被 SPA 回退接管,外部探测永远拿到 200 + index.html,健康检查形同虚设。)
- **静态资源**带内容哈希,`Cache-Control` 含 `immutable`;`index.html` 为 `no-cache`。
  同一响应只有一个 `Cache-Control` 头。
- **代理超时已显式设置**(2026-08-26 第 65 轮补):`proxy_connect_timeout 10s`、
  `proxy_read_timeout 600s`、`proxy_send_timeout 600s`、`client_body_timeout 300s`。
  不设置就全部走 nginx 默认的 **60 秒**——受控实测(同款配置 + 一个耗时 75s 的上游):
  请求在 **60.06 秒返回 504**,且是 nginx 的**裸 HTML 页面**,不经过应用的错误处理,
  前端拿不到任何可读信息。加上后同一请求 200/75.0s 正常返回;后端连不上时
  **10 秒**快速失败而不是让用户干等 60 秒。
  调整时注意:`connect` 要短(同网络内连不上应快速失败),`read/send` 要覆盖
  最长的合法操作(见 §7.2 的手动同步)但仍保留上界,以免后端挂死时连接被长期占用。
- **backend 每 10 秒自动重解析**:backend 容器重建后**无需重启 frontend**。
- 前端已做代码分割:react / antd / pdfjs 独立分块,业务代码更新不会让这些分块的浏览器缓存失效。

### 4.1 站点上的用户操作手册(`/manual`)

《用户操作手册》在站点上有一份在线版,供工厂用户随时查阅:

| 项 | 值 |
|---|---|
| 地址 | `https://coo.chongzhu.ai/manual`(等价的 `/manual.html` 也可用) |
| 入口 | 系统内右上角**头像菜单 →「用户操作手册」**,在新标签页打开 |
| 来源 | `docs/用户操作手册.md` |
| 生成 | `python3 scripts/build_manual_html.py` → `frontend/public/manual.html` |
| 打包 | vite 把 `public/` 原样拷进 `dist/`,随 frontend 镜像一起发布 |

**手册内容改了以后必须走完整条链路,否则站点上还是旧版**:

```bash
# 1) 改 docs/用户操作手册.md
python3 scripts/build_manual_html.py      # 2) 重新生成 HTML
docker compose build frontend             # 3) 重新构建镜像
docker compose up -d frontend             # 4) 发布
curl -s https://coo.chongzhu.ai/manual | grep -o '<title>[^<]*</title>'   # 5) 验证
```

几点实现说明:

- 生成脚本**只用 Python 标准库**,不需要 pip/npm 安装任何东西——客户 IT 拿到仓库要能直接跑。
  它只实现手册用到的 Markdown 子集(标题、列表、GFM 表格、围栏代码块、引用块、行内粗体/代码/链接);
  手册里若用到子集之外的语法,请在脚本里补,不要在手册里绕开。
- nginx 的 `location = /manual` 用 `try_files /manual.html =404` 而非 rewrite:
  **SPA 回退会把任何未命中的路径吐成 index.html**,手册文件一旦漏拷就会静默变成"打开是系统首页",
  反而看不出是缺文件;`=404` 才会明说。
- 该页是**公开可访问的静态页,不需要登录**。内容是操作说明、不含任何业务数据,
  但确实会暴露系统功能细节;若客户要求收敛,可在 Cloudflare Access 策略里一并覆盖 `/manual`。
- 页面为**单文件自包含**(CSS/JS 内联、无外部字体与 CDN),断外网也能正常显示;
  自带章节目录、关键词筛选、锚点链接与打印样式(可「打印 / 存为 PDF」分发)。

## 5. 日志与可观测性

### 5.1 日志格式

统一格式带时间戳、级别与来源:

```
2026-08-23 14:51:49 INFO    app.request | POST /api/orders 201 <- 203.0.113.9 user=admin 42ms
```

请求日志(`RequestLogMiddleware`)记录:**时间 / 方法 / 路径 / 状态码 / 真实客户端 IP / 用户身份 / 耗时**。

| 状态码 | 日志级别 | 用途 |
|---|---|---|
| 2xx/3xx | INFO | 常规 |
| 4xx | **WARNING** | 便于筛查越权、校验失败、限流 |
| 5xx | **ERROR** | 需要立即关注 |
| `/health` 且 <400 | DEBUG | 默认不打印,避免每 30 秒一条淹没业务日志 |

uvicorn 自带的重复访问日志已关闭。查看:

```bash
docker compose logs -f backend                      # 实时
docker compose logs backend --since 1h | grep WARNING
docker compose logs backend --since 24h | grep ERROR
```

### 5.2 审计日志(合规留痕)

- 存于数据库 `audit_logs` 表,**系统内没有任何删除或修改入口**;
- 保留期内(**≥3 年**)**勿清理该表**;
- 事件域:`auth` / `package` / `attachment` / `review` / `version` / `nas` / `export` / `org`;
- 每条含操作人、真实 IP、目标、时间、说明;下载与导出留痕含 IP 与行数/筛选条件;
- 管理员与审计查看人可在「操作日志」页查询与导出 Excel。

> 审计日志约 160 字节/行,百万行也只有约 160MB,MySQL 完全承受得住——**不要为"控制表大小"去清理它**。

## 6. 备份与恢复

### 6.1 每日备份

规格要求:每日一次,保留 30 天。一次执行会产出**两个配对的产物**:数据库与附件目录。

```bash
# 手动执行
/srv/platform/code/coo-docs/scripts/backup_mysql.sh

# 加入 crontab(每天 02:00 备份,每月 1 号 03:00 恢复演练)
crontab -e
0 2 * * * /srv/platform/code/coo-docs/scripts/backup_mysql.sh >> /var/log/coo_backup.log 2>&1
0 3 1 * * /srv/platform/code/coo-docs/scripts/restore_drill.sh >> /var/log/coo_drill.log 2>&1
```

**产物**(同一时间戳,请配对保存与恢复):

| 文件 | 内容 |
|---|---|
| `./backups/coo_{日期}_{时间}.sql.gz` | mysqldump 逻辑备份(`--single-transaction --routines --triggers --no-tablespaces`) |
| `./backups/coo_files_{日期}_{时间}.tar.gz` | `UPLOAD_DIR` 附件目录全量打包 |

两者都自动清理 `KEEP_DAYS`(默认 30)天前的文件。
可用环境变量覆盖:`BACKUP_DIR`、`KEEP_DAYS`、`UPLOAD_DIR`、`MYSQL_USER`、`MYSQL_PASSWORD`、`MYSQL_DATABASE`。

**脚本自带六道自检**,任一不满足即报错、删除残缺文件并以非零码退出(便于接入告警):

1. mysqldump 是否成功(容器未运行 / 认证失败);
2. 导出文件是否过小(< 1KB);
3. gzip 完整性(`gunzip -t`);
4. 是否含 `users` / `orders` / `attachments` / `audit_logs` / `system_settings` 五张关键表的建表语句;
5. 附件目录是否存在——**不存在直接报错而非静默跳过**(路径配错或挂载没起来时,静默跳过会让人以为备份是完整的);
6. 附件 tar 包完整性(`tar -tzf`),并打印文件数与包体积。

> **附件为什么用全量 tar**:文件按内容哈希命名、内容不可变(只增不改),全量打包最简单可靠。
> 数据量大到全量不划算时,可改为对同一目录做增量 `rsync`——**不可变意味着增量是安全的**。

> 云主机每日快照(保留 7 天)在 UCloud 控制台单独配置,作为整机层面的额外保护。

### 6.2 恢复演练(建议每月一次)

**备份能生成 ≠ 能恢复**,必须实际验证:

```bash
./scripts/restore_drill.sh                                     # 用最近一次备份
./scripts/restore_drill.sh backups/coo_2026-08-23_000703.sql.gz  # 指定文件
```

演练恢复到独立的 `coo_restore_drill` 库(**不触碰生产数据**),逐表比对 13 张表的行数,
再抽验中文编码、JWT 密钥、密码哈希、已放行锁定态、索引是否保真,
最后校验**演练库中被引用的每个附件文件都在同一时间戳的附件备份里**,
结束后自动清理演练库。任一项不符即以非零退出码返回。

> 最后那项检查是有来历的:此前演练只比对数据库侧,因此在"备份根本不含附件目录"的情况下**照样全绿**——
> **一个在缺口存在时仍然通过的演练比没有演练更危险**,因为它给出的是虚假保证。
> 现在若只有 `coo_*.sql.gz` 而没有配对的 `coo_files_*.tar.gz`,演练会明确报错并以非零码退出。

实测本环境恢复耗时约 **2–4 秒**,远优于规格要求的 RTO ≤ 8 小时。

### 6.3 真实恢复

确认要覆盖生产数据时:

```bash
STAMP=2026-XX-XX_XXXXXX                          # 数据库与附件必须用同一时间戳的一对
docker compose stop backend                      # 先停写入

# 1) 数据库
gunzip -c backups/coo_${STAMP}.sql.gz | \
  docker compose exec -T -e MYSQL_PWD=<密码> mysql mysql -ucoo coo

# 2) 附件目录(解包到 data/ 下,覆盖同名文件;内容寻址命名,同名即同内容)
tar -xzf backups/coo_files_${STAMP}.tar.gz -C data/
sudo chown -R 1000:1000 data/uploads             # 后端容器以 uid 1000 运行

docker compose start backend
```

**恢复后必须做的两件事**:

1. 执行 `storage_check.py` 核对是否出现**悬空记录**(库有记录、磁盘无文件)。
   若有,从 NAS 副本补回对应文件(§8.1)。
2. 数据库回到较早快照会让此后上传的附件变成**孤儿文件**,同样用 `storage_check.py` 核对与回收。

## 7. NAS 归档

### 7.1 归档目标配置(管理员,界面操作)

「NAS 归档 → NAS 配置」中维护:接入方式(**S3 兼容接口** / **本地挂载目录**)、端点地址、
Access / Secret Key、存储桶、区域、HTTPS 开关、每日同步时间、自动同步开关。

- 配置**存于数据库,保存后立即生效,无需重启**;
- 库中无记录时回退到 backend 环境变量(老部署无需任何改动);
- Secret Key **只写不读**——界面与接口都只返回掩码,**留空提交表示保持不变**;
- 每次变更写入操作日志(`nas / config_update`,记录归档目标、同步时间与重新归档数量,**不含密钥**)。

> **必须先「测试连接」再保存**。改错地址或密钥若不试连,要等到当晚自动同步失败才会暴露——
> 而那意味着该归档的核查证据当天没有留存。测试会区分"地址不通 / 密钥无效 / 桶不存在"给出具体原因,且不写库。

> **更换归档目标会触发全量重新归档**。系统按归档目标指纹判断:目标一变,全部历史附件重新标记为待归档,
> 并在返回中告知数量。这是必需的——新 NAS 必须拿到完整副本,否则它上面只有清单而没有文件。
> **首次同步的数据量等于历史全部附件,请安排在业务低峰执行。**

### 7.2 同步

- **自动**:每日按 `NAS_SYNC_TIME`(默认 01:00,**站点时区**)执行增量同步。
  > **2026-08-26 修复过一个静默失效**(第 59 轮,已跨过真实触发时刻实测):此前调度器用
  > "距下次触发还有多久"反推是否到点,而 `time.sleep()` 保证在截止时刻**当时或之后**才醒,
  > 于是每天都被判成"还差 86400 秒"而跳过——`sync_records` 里长期没有 `run_type='auto'` 记录,
  > 界面却只显示"上次同步成功"(那是上一次手动同步),**全程不告警**。
  > 现判据为「今天的计划时刻已到且今天还没跑过」,状态存数据库(重启不丢)。
  > **自愈行为**:服务若在计划时刻之后才启动、当天又没跑过,会在 1 小时内补跑一次
  > (只处理未同步附件,幂等)。
  > 巡检仍建议保留「`sync_records` 中当日是否有 auto 记录」这一项——
  > **不要用界面上的"上次同步成功"代替它**。
- **手动**:「NAS 归档」页点「立即同步」(COO 终审人与管理员可用)。
  > ⚠️ **手动同步是同步执行的,耗时随附件数线性增长。**
  > 实测(同机 MinIO)全量同步 **130 个附件耗时 5.04 秒**,约 **39ms/件**;
  > 按两年规模 12007 个附件线性外推约 **468 秒(近 8 分钟)**,而真实 NAS 在工厂内网、
  > 走加密隧道,每件成本只会更高。nginx 代理超时已放宽到 600 秒(§4),
  > 但**这只是把悬崖推远,没有消除它**。
  > **规模上来后请依赖每日定时同步**——它跑在后台线程里、不经过 HTTP,不受任何代理超时约束。
  > 若手动同步真的超时:**后端仍在继续跑**,不要立刻重试——重试会撞上同步互斥返回
  > 409「已有同步任务正在进行」,那不是第二次失败;稍后刷新「NAS 归档」页看结果即可。
- **单向、只增不删**(云端 → NAS)。
- **并发保护**:同步任务有进程内互斥。第二个手动请求返回 **409 +「已有同步任务正在进行,请稍后再试」**;
  调度线程撞上则记一条 info 跳过(待同步内容不会丢,手动那次会一并处理)。
  ⚠️ 横向扩展时需改为数据库层互斥。
- **失败自动重试**:失败的文件下次同步会自动重试。

### 7.3 归档目录规范

```
/COO核查/{项目代号}/{资料包编号}_{名称}/{版本号}/{文件}     ← 资料包版本线
/COO核查/{项目代号}/{资料包编号}_{名称}/{订单号}/{文件}     ← 客户订单线
```

每个目录含 `manifest.txt`(归档文件名 + 上传原名 + 字节数 + MD5)。
同目录内存在同名文件时,系统会追加内容哈希前 8 位区分(如 `发票__a1b2c3d4.pdf`),
**避免静默覆盖丢件**;不重名者保持原文件名以符合规格目录规范。
清单只列**确已归档到当前目标**的文件,绝不让清单与目录内容自相矛盾。

> **看到订单号/版本号目录带 `__` + 6 位十六进制后缀(如 `PO-2026_001__ab164a`)是正常的,不是异常。**
> 订单号不限制字符,而目录名里不能有路径分隔符——`PO-2026/001` 落到磁盘上会变成
> `PO-2026_001`,与另一张真名就叫 `PO-2026_001` 的订单**撞进同一个目录**,同名文件互相覆盖。
> 第 61 轮实测过这个后果:两张订单各传一份内容不同的同名文件,同步报告
> `success/failed 0`、数据库两条都标记已同步,而 NAS 上只剩一份——**先归档的那份静默丢失**。
> 因此凡是订单号/版本号经过字符清洗**被改动过**的,目录名会追加原值的短哈希以保证一一对应;
> 未被改动的(目前全部 127 个订单号与 33 个版本号)保持原样,目录名不变。
> **要确认某个带后缀的目录属于哪张订单,看该目录 `manifest.txt` 的首行**,那里写的是真实订单号。
>
> 资料包名中的 `/`(如 `原材料/零部件采购订单`)仍按原有方式替换为 `_`,目录名不受本机制影响。

### 7.4 定期核对归档完整性

```bash
docker compose exec backend python scripts/storage_check.py --check-nas
```

从归档侧**反向核对**每份清单列出的文件是否真的存在。

> 订单/版本从数据库删除后,NAS 上的清单不会被自动清理(同步只增不删),
> 会留下"列着文件却没有文件"的目录——这类问题**只能靠巡检发现**,代码路径永远走不到。
> 加 `--fix-nas-manifests` 可将其改写为真实内容(**不删除任何归档文件**)。

### 7.5 NAS 不可达时的行为(已实测)

- `/nas/status` 如实报告 `可达=False`(约 1.8 秒的连接超时);
- 手动同步返回 `status=failed` 并给出「NAS 不可达或 S3/MinIO 未连通」;
- **业务完全不受影响**:工作台/订单/待办/受控区/资料包连同上传、下载全部正常;
- 中断期间上传的附件正确排队,恢复后自动补齐。

生产按规格书第四章用 frp / Tailscale 打通工厂 NAS,在「NAS 配置」中把端点地址指向隧道内的
NAS S3 兼容服务(群晖 / 威联通均支持)。**隧道中断只影响当日归档**。

## 8. 附件存储运维

### 8.1 一致性巡检

附件按内容 sha256 命名落盘,数据库记录与物理文件应一一对应。

```bash
docker compose exec backend python scripts/storage_check.py                  # 只报告
docker compose exec backend python scripts/storage_check.py --purge-orphans  # 确认后回收孤儿文件
```

| 偏差 | 含义 | 严重性 | 处理 |
|---|---|---|---|
| **悬空记录** | 库有记录、磁盘无文件 | 🔴 **证据丢失**,审计调阅会 404 | 紧急。从 `coo_files_*.tar.gz` 附件备份恢复(§6.3);实在没有再从 NAS 副本人工重建 |
| **孤儿文件** | 磁盘有文件、库无记录 | 🟡 静默占用数据盘 | 确认后 `--purge-orphans` 回收 |

悬空时脚本以非零退出码返回,便于接入告警;NAS 同步也会把它报为「源文件缺失」。
常见孤儿来源:数据库恢复到较早快照、直接用 SQL 清理记录、写库失败的残留。

### 8.1b 数据库结构自检(索引是否都在位)

```bash
docker compose exec backend python scripts/schema_check.py    # 退出码 0=全部就位 / 1=有缺失
```

启动时会尽力补建索引,但历史库、数据库账号缺 INDEX 权限、锁等待都可能让某个索引建不出来。
**第 75 轮之前这类失败在默认日志级别下零输出**——服务照常启动、照常提供服务,
只是从此少了一个索引,症状要等规模上来才显现(变慢),而那时没有任何线索指向真正的原因。
现已改为:启动时做收尾校验,缺失则记 **WARNING** 并列出具体索引名;正常时记一条
「索引核对通过:N 个应有索引全部就位」。

**这不是可有可无的优化。** 第 74 轮实测:5 万订单规模下,这些索引让订单列表从
全表扫描 + filesort 变成只扫 62 行的反向索引扫描;30 万条审计日志同理。
少一个索引等于把一个已验证的优化悄悄拿掉。

建议与 `storage_check.py` 一同纳入巡检并按退出码接监控。

### 8.2 原子写入(无需运维干预,但要知道)

- 附件落盘用「临时文件 + fsync + `os.replace`」原子替换,不会出现"文件已存在但只写了一半"被别的请求复用的窗口;
- 本地挂载模式的归档拷贝与清单改写同样是原子替换——核查方在归档目录里不会读到半截文件;
- S3 模式由服务端保证原子性。

### 8.3 ZIP 导出临时目录

ZIP 导出会在 **`./data/uploads/.zip-tmp`** 写临时文件,响应结束后由后台任务删除。

- **磁盘余量**:该目录的峰值占用约等于「同时进行的导出数 × 单个包体积」。
  两年规模下单个订单包可达几百 MB,请为数据盘保留相应余量。
- **残留清理**:进程被强杀时可能留下 `export-*.zip`。这类文件**不会**被 `storage_check.py` 报为孤儿
  (它只扫描上传目录下的文件,不进子目录),需要手工检查:
  ```bash
  ls -la data/uploads/.zip-tmp/
  find data/uploads/.zip-tmp -name 'export-*.zip' -mmin +120 -delete   # 清理 2 小时前的残留
  ```

### 8.4 资源基线(实测,供容量规划参考)

| 项目 | 实测值 |
|---|---|
| 审计日志 | 约 160 字节/行;100 万行 ≈ 160MB |
| ZIP 导出内存 | 与包体积无关,约 +3.8MB(此前是 +92MB) |
| ZIP 导出耗时 | 94MB 的包约 4.4 秒(21.5 MB/s) |
| Excel 导出内存 | 10 万行峰值约 49MB(此前 302MB) |
| Excel 导出耗时 | 10 万行约 36 秒 |
| 长时运行 | 连续 17 小时:后端线程 7 个无累积、MySQL 连接峰值 5/151 无泄漏 |
| 两年规模 | 约 205 订单 / 1203 实例 / 12007 附件(压测验证过) |

| 监控项 | 方式 | 告警条件 |

| 站点可用性 | HTTP GET `https://coo.chongzhu.ai/health` | 非 200,或响应体 `db != "up"` |

| 存储一致性 | `storage_check.py` 退出码 | 非零(存在悬空记录) |
| 数据库结构 | `schema_check.py` 退出码 | 非零(应有索引/列缺失,见 §8.1b) |
| NAS 归档 | 「NAS 归档」页 / `sync_records` 表 | 连续两天同步失败,或待同步数持续增长 |
| 磁盘 | `df` | 使用率 > 80% |
| 错误日志 | 日志采集 | 单位时间 ERROR 数突增 |

**`/health` 的行为(已实测)**:

| 情况 | 返回 |
|---|---|
| 正常 | `200 {"status":"ok","app":"...","db":"up"}` |
| 数据库不可达 | **`503` 且 `db: down`** |

该端点会真正执行一次 `SELECT 1`,不是静态字符串;nginx 单独 location 反代并标 `no-store`,
**不被任何层缓存**。compose 中 backend 已配 healthcheck(30s 间隔),依赖挂掉约 75 秒后容器标记 `unhealthy`。

> **实测的自愈能力**:MySQL 重启后后端 **16 秒自愈**(`pool_pre_ping` 生效,无需重启后端);
> 数据库不可用期间业务接口返回 **503 + 可读中文提示**(而非 500),恢复后 5 秒内 `/health` 转 200。

## 11. 安全运维

### 11.1 JWT 密钥轮换

管理员登录 →「组织管理 → 安全设置 → 轮换密钥」。

- 用途:怀疑令牌泄露,或需要强制全员下线;
- **轮换后所有人(含本人)需重新登录**;
- 密钥存于数据库 `system_settings` 表,不在代码/配置中;
- 操作记入审计日志 `org.jwt_secret_rotate`。

### 11.2 账号安全

- 连续 5 次密码错误锁定 30 分钟(`MAX_LOGIN_FAILURES` / `LOGIN_LOCK_MINUTES` 可调);
  管理员重置密码可立即解锁。
- 停用账号**立即失效**:已登录会话在下次请求时被清除令牌并跳转登录页。
- **防自锁保护**:系统拒绝停用当前登录账号,以及停用/降级最后一个启用状态的管理员。
- 密码重置留痕包含操作人——"谁重置了谁的密码"可追溯。

### 11.2b 查询 `system_settings` 表时的注意事项

该表同时存放 **JWT 签名密钥**(`jwt_secret_key`)与 NAS 配置(`nas_config`,含 Secret Key)。
**不要 `SELECT *` 一把取整表**——密钥会明文进入终端输出、shell history 与日志。按需取行:

```bash
docker compose exec -T -e MYSQL_PWD=<密码> mysql mysql -ucoo coo \
  -e "SELECT \`value\` FROM system_settings WHERE \`key\`='nas_config';"
```

若密钥不慎被打印,按 §11.1 轮换一次即可(全员重新登录,约 1 分钟影响)。

### 11.3 轮换数据库 / MinIO 口令

用 `scripts/install.sh` 部署的实例,口令本就是随机生成的,**通常不需要这一节**。
需要轮换(口令外泄、人员变动、或从旧的弱默认值升级)时按下面做。

⚠️ **只改 `.env` 是不够的**——那些变量只在数据库首次初始化时生效,
库已经建起来之后改它只会让后端连不上。必须先在库里 `ALTER USER`,再改 `.env`。
⚠️ 新口令**只用字母数字**:它会被拼进 `DATABASE_URL`,`@ : / ? #` 会被当作 URL 分隔符。

```bash
set -a && . ./.env && set +a         # 取当前口令
NEW=$(LC_ALL=C tr -dc 'A-Za-z0-9' < /dev/urandom | head -c 32)

# MySQL(需短暂停机窗口)
docker compose exec -T -e MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql mysql -uroot \
  -e "ALTER USER 'coo'@'%' IDENTIFIED BY '$NEW'; FLUSH PRIVILEGES;"
sed -i "s/^MYSQL_PASSWORD=.*/MYSQL_PASSWORD=$NEW/" .env    # 只改这一处即可
docker compose up -d backend                                # DATABASE_URL 由 .env 拼出
./scripts/backup_mysql.sh                                   # 立刻验证备份脚本仍能工作
```

备份脚本读的是同一批 `MYSQL_*` 变量(cron 行里已 `. ./.env`),**不需要再改脚本**。

MinIO:改 `.env` 的 `MINIO_ROOT_USER/PASSWORD` 后重建容器,并在**界面的「NAS 配置」**里同步
Access/Secret Key(注意:界面配置优先于环境变量)。

### 11.4 接口限流

内置,无需配置,按客户端**真实 IP** 滑动窗口计数:

| 接口 | 限额 |
|---|---|
| `/api/auth/login*` | **60 次 / 分钟 / IP** |
| 其余接口 | **1200 次 / 分钟 / IP** |

超限返回 429 +「请求过于频繁,请稍后再试」。

> 登录阈值放宽到 60 是有意为之:暴力破解的主闸是**账号级失败锁定**(5 次锁 30 分钟),
> 而整厂共用一个出口 IP 时换班集中登录很容易撞上过严的 IP 阈值。
> ⚠️ 计数在进程内存中,**多实例部署需换共享存储**。

### 11.5 其他内置防护

- 上传文件按**文件头**校验名实相符,拒绝伪装文件与空文件;`mime_type` 由服务端按扩展名判定,不采信客户端;
- 预览白名单仅含 PDF 与图片,响应一律 `attachment` 下发(HTML 伪装成 .pdf 无法内联执行);
- 附件下载走**短时效票据**(HMAC 签名、60 秒过期、绑定具体附件与具体用户);
  签发端点走与常规请求完全相同的权限判定,请求日志只记 `url.path` 不含查询串;
  **审计留痕仍记录真实操作人与 IP**;
- Excel 导出所有单元格强制字符串类型,`=` 开头内容不会被 Excel 当公式执行(防公式注入);
- 审计检索的 LIKE 通配符已转义(`%`、`_` 按字面匹配);非法日期返回 400 而非 503;
- 前端全站唯一动态导航目标(通知跳转)有站内路径白名单校验。

## 12. 故障排查

| 现象 | 排查与处理 |
|---|---|
| 页面 502 | backend 未就绪或崩溃:`docker compose logs backend`。nginx 每 10s 自动重解析 backend IP,容器重建后**无需重启 frontend** |
| 接口 503 +「数据库暂时不可用」 | MySQL 故障或重启中。`docker compose ps mysql`;后端会自愈(约 16 秒),无需重启 backend |
| `/health` 返回 503 且 `db: down` | 同上。这是**正确行为**,说明探活在工作 |
| backend 容器 `unhealthy` | 依赖(MySQL)不可达超过约 75 秒。先修依赖 |
| 登录报「账号已锁定」 | 等 30 分钟,或管理员重置密码 |
| 大量 429 | 触发限流。确认是否整厂共用出口 IP、是否有异常流量;必要时调整 §11.4 阈值 |
| 上传报 400「文件超过 100MB 上限」 | 单文件上限 `MAX_FILE_MB`;nginx 请求体上限 200MB。两者需同步调整 |
| 上传报 413 | nginx `client_max_body_size` 不足 |
| 上传被拒「文件内容与扩展名不符」 | 文件头校验拦下。确认文件是真实格式而非改名 |
| 下载报 403 / 票据无效 | 票据 60 秒过期,或跨附件/跨用户使用。回系统内重新点下载 |
| 导出报 400 要求缩小范围 | 审计导出命中超过 10 万条上限 |
| 导出 ZIP 很慢或失败 | 检查 `data/uploads/.zip-tmp` 所在盘余量(§8.3) |
| PDF 预览空白 | 强制刷新(Ctrl+F5);确认 `/assets/*.mjs` 返回 `Content-Type: text/javascript`;也可能是该 PDF 本身无可见内容 |
| 全员突然要求重新登录 | 属正常:JWT 密钥被轮换(查审计日志 `org.jwt_secret_rotate`),或后端首次生成密钥 |
| 用户报"看不到某个订单" | 订单按**工厂**隔离。检查该账号的工厂授权 |
| 用户报"审核按钮不见了" | 职责分离规则(本部门有其他审核人时不能审自己提交的内容),或条目不在其审核阶段 |
| NAS 同步失败 | 「NAS 归档」页看失败清单 + `docker compose logs backend`。常见为 S3 端点不可达或凭据错误——在「NAS 配置」点「测试连接」即可定位。失败文件下次自动重试 |
| NAS 手动同步返回 409 | 已有同步在跑(每日调度或另一次手动)。等它跑完 |
| **待同步数持续增长、`sync_records` 无当日 auto 记录** | 先确认 `auto_sync` 是否被关掉、`sync_time` 是否被改;再看 backend 日志有无 `app.scheduler` 行。手动触发同步作为临时措施(§7.2) |
| 归档目录"有清单没文件" | 对应订单/版本已从库中删除。用 `--check-nas` 核对,`--fix-nas-manifests` 改写清单 |
| 悬空记录告警 | 🔴 证据丢失。从 NAS 副本或备份恢复对应文件,详见 §8.1 |
| 宿主重启后服务未起 | 所有服务已配 `restart: unless-stopped`;若仍未起:`docker compose up -d` |
| 站点整体不可达但本机 `curl localhost` 正常 | 隧道问题:`systemctl status cloudflared`、检查 ingress 规则顺序 |

## 13. 升级

```bash
cd /srv/platform/code/coo-docs
./scripts/backup_mysql.sh          # 升级前先备份
git pull
docker compose build
docker compose up -d               # 数据卷与上传目录不受影响
docker compose ps                  # 确认 healthy
docker compose logs backend | tail -30   # 确认无 ERROR,注意"已补建列/索引"提示

```

**回滚**:`git checkout <上一个可用提交> && docker compose build && docker compose up -d`。
若新版本改过表结构,回滚代码后**旧代码不认识新列但不会报错**(新增列可为空);
若确需回滚数据,按 §6.3 从升级前的备份恢复。

### 13.1 从旧版本(root 容器 / 环境变量密钥时代)升级的注意事项

1. **上传目录属主**:后端容器现以 uid 1000 运行。旧版本以 root 写入的文件会导致上传报 500。升级前执行:
   `sudo chown -R 1000:1000 ./data/uploads ./nas_mount`(目录不存在则先 `mkdir -p`)。
2. **全员重新登录一次**:JWT 密钥改为数据库存储,升级后首次启动生成新密钥,旧登录态全部失效,属预期的一次性影响。
3. **`SECRET_KEY` 环境变量已彻底失效**:设置它不会有任何作用;轮换密钥一律走界面。
4. **已存在的演示账号不会被自动停用**:`SEED_DEMO_DATA=false` 只约束"新建"。请在组织管理中逐个停用,并修改 admin 密码。
5. **端口收敛**:3306/8000/9000/9001/8001 已改为仅绑定 127.0.0.1。此前从其他机器直连这些端口的工具
   (数据库客户端、BI 等)会连接失败,需改走 SSH 隧道:
   `ssh -L 3306:127.0.0.1:3307 用户@服务器`(宿主侧映射为 3307)。
6. **防自锁保护**:系统会拒绝停用当前登录账号,以及停用/降级最后一个启用状态的管理员。
7. **表结构自动补齐**:启动期 `_ensure_columns()` / `_ensure_indexes()` 会为历史库补建后加的列与索引,
   **无需手工迁移**;日志中会有对应提示。

### 13.2 扩容前置条件

多进程 / 多实例部署**不在一期范围**。横向扩容前必须先改造:

- 接口限流:进程内内存计数 → 共享存储(Redis);
- NAS 调度器:进程内线程 → 外部 cron 或分布式调度;
- NAS 同步互斥:进程内锁 → 数据库层互斥;
- JWT 密钥轮换已支持多进程收敛(解码失败自动回源),但仍建议整体评估。
